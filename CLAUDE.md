# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Jig is a single-user cloud library of code snippets. It has two front doors onto the same data layer:
- A Next.js 16 dashboard (App Router, React 19, Tailwind 4) behind a password login.
- An MCP endpoint at `/api/mcp` (Streamable HTTP, bearer-token auth) that coding agents call to search, fetch, create, update and restore snippets.

The package manager is Bun (`bun.lock`).

## Commands

```bash
bun install
cp .env.example .env.local   # set ADMIN_PASSWORD, SESSION_SECRET and JIG_ENCRYPTION_KEY
bun run dev                  # next dev
bun run build / bun run start
bun run typecheck            # tsc --noEmit
bun run test                 # bun test lib (in-memory PGlite, no DB needed)
bun test lib/snippets.test.ts -t "slugify"   # a single test or describe block by name
```

If `DATABASE_URL` is unset, the app uses PGlite (Postgres compiled to WASM) and stores data in `.data/pglite`. If it is set, the app uses Neon's HTTP driver. Other env vars: `ADMIN_PASSWORD`, `SESSION_SECRET` (falls back to `ADMIN_PASSWORD`), `JIG_TIMEZONE` (default `Australia/Sydney`), and `JIG_ENCRYPTION_KEY` (32 bytes base64, needed only for credentials).

## Architecture

**Data layer (`lib/`)**: all business logic lives here and takes a `Db` as its first argument. This lets tests pass an in-memory PGlite, while the app passes `getDb()`.
- `lib/db.ts`: a minimal `Db { query(text, params) }` interface with two drivers. The schema is a list of `CREATE ... IF NOT EXISTS` statements that runs on first use, so there are no migration files. To change the schema, edit `SCHEMA` and make sure every statement stays idempotent.
- **No interactive transactions.** Neon's HTTP driver can't hold one open, so each write must be a single SQL statement. Multi-table writes use CTEs (`WITH s AS (INSERT/UPDATE ... RETURNING) INSERT ...`). Keep to this pattern.
- `lib/snippets.ts`: CRUD and versioning. `snippets` holds the latest metadata and `current_version`. `snippet_versions` holds a **full snapshot** of every version (not deltas), including files, instructions and dependencies, which are stored as jsonb.
  - `insertVersion` bumps the version with `WHERE current_version = expected` as an optimistic lock. If a concurrent save wins, this one throws a `SnippetError("conflict")`. `baseVersion` in a patch gives agents the same protection explicitly.
  - An update that leaves every content field unchanged saves nothing (`changed: false`).
  - A restore never rewrites history. It saves a copy of the old version as a new version.
  - Errors callers are meant to see are `SnippetError` with code `not_found | conflict | invalid`. Anything else is treated as a server error.
- `lib/validation.ts`: Zod schemas (Zod 4) shared by the dashboard and MCP. They cover slug format, size caps and the dedupe of tags and dependencies.
- `lib/languages.ts`: the allowed language ids. Each id doubles as its Shiki grammar name, and file extensions map to languages.
- `lib/diff.ts`: version-to-version diffs of metadata fields and per-file unified diffs. The dashboard's `DiffView` uses these, and so does the MCP `diff_snippet_versions` tool.
- `lib/ai.ts`: the dashboard's AI helpers, on Google's Gemini API (`@google/genai`, falls back to Flash-Lite when busy) or on OpenRouter (plain `fetch`, GLM Flash then DeepSeek Flash, `provider: { data_collection: "deny", ignore: CHINA_HOSTS }` so prompts only go to non-China hosts that don't keep them). The key that's set picks the provider; `JIG_AI_PROVIDER` decides when both are: `rewrite` (rephrase, shorten, fix; markdown in and out) for the note editor's AI menu (`components/NoteAi.tsx`), and `review` (JSON issues with file and line) for a snippet's Check for errors (`components/SnippetReview.tsx`). Optional: the buttons only render when `GEMINI_API_KEY` or `OPENROUTER_API_KEY` is set (`aiEnabled()`); `JIG_AI_MODEL` overrides the provider's main model. Rewrites ask Gemini for `thinkingLevel: LOW` (Gemini 3's documented control; its default "medium" made a one-paragraph rephrase take ~7s), reviews keep the default. Suggestions are never saved by themselves: a rewrite goes into the editor and the note's Save makes the version. The server actions refuse locked notes; credentials are never sent. `lib/mcp.ts` has no reason to import it.
- `lib/oauth.ts` + `lib/oauth-http.ts`: OAuth 2.1 for the MCP endpoint, so Claude's custom connectors can sign in instead of pasting a token. Jig is its own authorization server: discovery under `app/.well-known/`, dynamic registration, token and revoke routes under `app/oauth/` (public in `proxy.ts`), and the consent page `app/oauth/authorize` (needs the dashboard login; it shows the host the approval goes back to, since any app can call itself Claude). Public clients only, PKCE S256 required, codes are one-use for 5 minutes, access tokens last an hour, and refreshing rotates both tokens. Only hashes are stored. An approved app gets what an API token gets; the Connect page lists and disconnects them.
- `lib/trash.ts`: Recently deleted. Deleting from the dashboard moves the item's row and every version into `trash` (one CTE statement), so no other query has to skip deleted rows; restoring moves it back with the same id, so its lock, secrets and share links return (under the next free slug if its own was taken). Items go for good after 30 days, purged lazily whenever something is deleted or the page is listed, along with their share links.
- `lib/tokens.ts`: MCP API tokens (`jig_...`). Only the SHA-256 hash is stored, and `verifyToken` also updates `last_used_at`.
- `lib/credentials.ts` + `lib/crypto.ts`: dashboard-only credentials. Secret field values are AES-256-GCM ciphertext bound to `<credential id>:<field id>`, and `revealField` is the only function that returns plaintext. Revealing a secret, copying a credential link again or making one needs the same unlock as locked notes (`isUnlocked()`). **`lib/mcp.ts` must never import these, directly or indirectly**; `lib/mcp.test.ts` fails if it does. Notes (`lib/notes.ts`) mirror the snippet versioning pattern and are exposed over MCP.
- `lib/shares.ts` + `lib/share-pass.ts`: share links (`/s/<token>`, public, excluded from the proxy). Only token hashes are stored; credential links need a scrypt-hashed passcode and lock after 5 failures (`checkPasscode` takes the try atomically before checking, so parallel guesses can't exceed it); `recordView` counts atomically in one statement. `shares.ts` reads credentials, so **`lib/mcp.ts` must never import it either.** The public actions live in `app/share-actions.ts`: every export of a `"use server"` file is callable by anyone, so keep helpers (like issuing a pass) out of it.
- `lib/locked-notes.ts` + `lib/passkeys.ts`: locked notes and passkeys. A locked note (`notes.locked_at`) has every version's body encrypted with the credentials key, bound to `note:<id>:<version>`. `lib/notes.ts` stays key-free: functions take an optional `NoteCodec`, and without one a locked note reads as empty with `unreadable: true` and can't be changed. The dashboard passes `unlockedCodec()`, which only returns the codec while the signed `jig_unlock` cookie is valid (30 minutes, a session cookie so closing the browser locks again, and tied to the session it was made in) (set by a passkey or the dashboard password, rate limited like login). The same unlock opens credential secrets. MCP hides locked notes entirely (`hideLocked`, `refuseLocked`); **`lib/mcp.ts` must never import `locked-notes.ts`**, and the test checks that too. Passkeys are WebAuthn via SimpleWebAuthn, discoverable and user-verified, tied to the request's host (a passkey made on the deployed site doesn't work on localhost); the challenge travels in a signed `jig_webauthn` cookie tied to its use (login, unlock or register). `JIG_ORIGIN` pins the RP ID when set. `passkeyPromptOptions` and `loginWithPasskey` are deliberately public actions (they run before a session exists).
- `lib/ratelimit.ts`: failed logins counted per IP in `login_attempts`, plus a ceiling across all IPs for password attempts (passkey sign-in skips it, so the owner can still get in). The attempt is recorded before it is counted, so parallel requests can't bypass the limit. Login needs the DB and fails closed. `ADMIN_PASSWORD` must be at least 12 characters (`passwordProblem`).
- `lib/signing.ts`: every signed cookie (session, share pass, passkey challenge, unlock) goes through `seal`/`unseal`, with a key per purpose derived (HKDF) from a random secret the DB makes for itself (`app_secrets`) plus `SESSION_SECRET` (or `ADMIN_PASSWORD`) plus `JIG_ENCRYPTION_KEY`. **Never sign anything with the password alone**: share passes and challenges are handed to strangers, and would let them guess it offline.

**MCP (`lib/mcp.ts` + `app/api/mcp/route.ts`)**: `registerTools` registers the tools on `mcp-handler` / `@modelcontextprotocol/server`. `SERVER_INSTRUCTIONS` is the guidance agents receive. Tool output is formatted markdown text, not JSON. Every handler is wrapped in `run()`, which turns a `SnippetError` into an `isError` result. Each version records who saved it in its `source` field: `mcp:<token name>` for agents, `web` for the dashboard. Deleting a snippet is deliberately **not** exposed over MCP.

**Auth has two layers**:
- `proxy.ts` (the Next 16 replacement for middleware) only checks that a session cookie is present and unexpired (it has no database, so it can't check the signature), and redirects to `/login` otherwise; `/login`, `/s/` and the icons are public. It also sets the nonce Content-Security-Policy, which is why the root layout calls `connection()` (a page rendered ahead of time would have scripts without the nonce). Other security headers are in `next.config.ts`.
- `requireAuth()` in `lib/auth.ts` is the real guard: it verifies the signature and that the session wasn't ended by "Sign out everywhere" (`sessions-valid-after` in `app_secrets`). Sessions last a week from their last renewal (`syncPreferences` renews them) and 30 days at most. **Every server action in `app/actions.ts`, and every page and layout under `app/(app)/`, must call it first**: layouts don't re-run on client navigation, so the layout's check doesn't cover pages. `lib/guards.test.ts` checks both.
- Actions called from client code return `{ error }` rather than throwing; `app/(app)/error.tsx` and `app/global-error.tsx` catch the rest.
- `/api/mcp` uses bearer tokens through `withMcpAuth` instead: an API token (`jig_...`) or an OAuth access token (`jigo_at_...`). Its 401 points at `/.well-known/oauth-protected-resource/api/mcp`.
- `getDb()` keeps its instance on `globalThis`: `next dev` bundles route handlers and pages apart, and two PGlite copies over one folder drift apart.

**Dashboard (`app/`)**: pages under the `(app)` route group are server components that call `lib/` directly. In list layout each section's `layout.tsx` renders a split view (a client-side filtered column beside the page); preferences (tab order, each list's layout and sort) are read from cookies (`lib/prefs.ts`, `lib/view.ts`), so pages never wait on them; `lib/settings.ts` keeps the saved copy in the `settings` table. Changing one saves both (`savePreference`, `setViewPreference`); a browser copies the saved ones into its cookies on login and, via `PrefsSync`, at most every 5 minutes in the background. **Don't add `<Suspense>` boundaries or `loading.tsx` under `(app)`**: pages inside them rendered but never finished hydrating (no effects, so the code and notes editors never appeared). The split list reads `?q=` from `window.location` after mount instead of `useSearchParams` for the same reason. Mutations go through the server actions in `app/actions.ts`. The snippet form sends all its fields as a single JSON `payload` form field so the file list stays structured.

**Build config** (`next.config.ts`): PGlite must remain in `serverExternalPackages`, because bundling it breaks its WASM file lookups. `outputFileTracingRoot` and the Turbopack root are pinned to this directory so a lockfile in a parent folder is never picked up.

**Distribution**: each user deploys their own copy with the README's Deploy with Vercel button, which also provisions a Neon database (`stores` param) and asks only for `ADMIN_PASSWORD` and `JIG_TIMEZONE`. Keep new required configuration optional or self-provisioning, and never add schema changes that aren't idempotent, since existing copies apply them on their next request.
